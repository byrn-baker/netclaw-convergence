# Spec 153 research: IDE, assistants, Windows handoff and Spec Kit

Research date: **2026-10-17**. Scope: R1, R12, R13, R15. This is design research, not acceptance evidence. No real runtime home, credential, external registration or installation was accessed or changed. The only authored file is this research note. Root owns the GAIT session.

## R1 — Windows gate and WSL handoff

**Decision.** Keep `extensionKind: ["workspace"]`. Native Windows is a prerequisite gate; actual setup runs only when `process.platform === "linux"` and `vscode.env.remoteName === "wsl"`, with the selected distribution and `/etc/os-release` verified. Local macOS remains the other setup target. Other Linux/Remote SSH contexts retain existing management, but cannot claim new-installer qualification.

The existing extension already declares workspace execution in `extensions/netclaw-vscode/package.json`. Microsoft's [remote extension architecture](https://code.visualstudio.com/api/advanced-topics/remote-extensions) documents workspace extensions running beside the workspace and a VS Code Server matching the client version. The selected extension host, not the renderer OS or terminal shell name, determines where subprocesses and paths belong. **Accessed 2026-10-17.**

**Read-only probes.** Resolve the Windows system `wsl.exe` and run bounded argument arrays, never shell-concatenated commands: `--status`, `--list --quiet`, and `--list --verbose`. Check the installed WSL extension with `vscode.extensions.getExtension("ms-vscode-remote.remote-wsl")`; separately check available commands before offering a handoff. Unknown, failed or unparsable evidence is a stop, not an empty-success result. Do not execute a Linux command during the gate: doing so can start a distribution. Do not call install/update/set-version/set-default/terminate/shutdown or DISM/elevation commands. `--status` is supplementary; per-distribution version comes from the verbose list, not the machine default.

Microsoft's [WSL command reference](https://learn.microsoft.com/en-us/windows/wsl/basic-commands) identifies `--list --verbose` as the installed-distribution/state/WSL-version query and `--quiet` as names only. The [WSL installation guide](https://learn.microsoft.com/en-us/windows/wsl/install) is the remedy destination; remediation is performed by the owner outside the gate. The [official WSL extension listing](https://marketplace.visualstudio.com/items?itemName=ms-vscode-remote.remote-wsl) establishes the extension ID. **Accessed 2026-10-17.**

**Encoding/parser decision.** Capture buffers. Set `WSL_UTF8=1` for each probe, but support UTF-16LE as well, including output without a BOM; validate a complete decode rather than stripping NULs from arbitrary data. Join verbose rows to the separately observed quiet names, taking the trailing numeric WSL version and the leading default marker. Do not split distribution names on arbitrary spaces or depend on translated headers/status words. Fail closed on duplicate, ambiguous or malformed rows. Test UTF-8, UTF-16LE, BOM/no-BOM, CRLF, non-ASCII names, spaces, default markers and localized errors.

The [Microsoft WSL implementation](https://github.com/microsoft/WSL/blob/master/src/windows/common/WslClient.cpp), inspected directly, selects `_O_U8TEXT` for `WSL_UTF8=1`, otherwise `_O_U16TEXT` (around lines 1882–1890). `ListDistributions` prints `*` for the default and `entry.Version` as the last field (around lines 705–786). The [official diagnostic script](https://raw.githubusercontent.com/microsoft/WSL/master/diagnostics/collect-wsl-logs.ps1) independently sets `WSL_UTF8=1`. These are mutable upstream sources, so retain regression fixtures rather than assuming all installed WSL generations behave identically. **Accessed 2026-10-17.**

**Distribution policy.** Make the allowlist explicit: Ubuntu **24.04 LTS and 26.04 LTS**, subject to Spec 153 qualification on each claimed architecture. Do not infer the release solely from a name such as `Ubuntu`, or equate WSL support with NetClaw support. A Windows list supplies a candidate distribution identity; after the user chooses to reopen, Linux-side `ID=ubuntu` and exact `VERSION_ID` must pass before acquisition/remedies/setup. An imported or generically named distribution whose identity cannot be established in the native gate should be described as **requires identity verification in WSL**, not already qualified. Older Ubuntu and other distributions remain unsupported for this installer until separately qualified.

Canonical lists [24.04 and 26.04 as supported LTS releases](https://ubuntu.com/about/release-cycle). Local `specs/148-hermes-hud-integration/closure.md:62` records actual prior Ubuntu 26.04 WSL evidence and explicitly leaves 24.04 unverified. Prior evidence is useful context, not Spec 153 acceptance. **Accessed 2026-10-17.**

**Handoff design.** The gate itself writes no resume file. The explicit **Reopen in WSL** action starts a separate, disclosed handoff: it may start the chosen distribution, create only a private non-secret setup-session directory/record, and let VS Code install/start its own remote server. The native side sends schema-validated JSON through stdin to a fixed, bounded handoff helper; no answers enter shell code. The record contains schema/session IDs, selected distribution, expiry, answer revision and non-secret answers only. It contains no approval token or capability to apply. The helper returns the exact Linux session directory, then `vscode.openFolder` opens its `vscode-remote://wsl+<distro>/<session-directory>` URI. The remote extension imports the record, verifies the destination authority and Linux identity, writes its private resume state, and continues the wizard. A malicious/replayed record can at most recreate an unreviewed draft. Re-check prerequisites and obtain a fresh review before apply.

This deliberately makes the gate/handoff boundary explicit. It requires a short specification clarification in wording: the **read-only prerequisite gate** ends at the user's handoff action; the handoff's disclosed private state write is not NetClaw provisioning. Without that distinction, the plan's existing “resume record on the WSL side” contradicts an absolute no-write interpretation of the native-window requirement. Preserve every non-secret answer with round-trip fixtures; never assume local and remote `globalState` or `globalStorageUri` are the same store.

Microsoft documents [the WSL URI/CLI launch route and first-open server setup](https://code.visualstudio.com/docs/remote/wsl), including `code --remote wsl+<distro> <path>` and `--folder-uri vscode-remote://...`. The public [`vscode.openFolder` command](https://code.visualstudio.com/api/references/commands) accepts a URI and can replace the window, shutting down the current extension host. Thus persist the handoff before opening it. Prefer this documented URI/public command route over an undocumented Remote-WSL command ID/signature; offer the documented **WSL: Connect to WSL using Distro** command as a user-facing recovery route. **Accessed 2026-10-17.**

**Rejected alternatives and limits.** No registry schema dependency; no English-only parsing; no `wsl --install` remedy inside the extension; no automatic WSL1 conversion; no default-distro mutation; no guess that a distro named Ubuntu has a supported release; no automatic handoff before user selection. The handoff implementation still needs real Windows/WSL acceptance, including absent/disabled WSL extension, stopped distributions, unknown OS identity, empty VS Code windows, expiry, interrupted handoff and unchanged gate snapshots. macOS tests cannot establish these outcomes.

## R12 — Assistant surfaces, runtime launch, skills and broker

**Node-free launch decision.** Use the current extension host's absolute `process.execPath` for all three MCP clients and the bundled `dist/assistant.mjs`, with `ELECTRON_RUN_AS_NODE=1`. In a local desktop host this invokes the editor Electron runtime as Node; in WSL it uses the remote server runtime. This means no separately installed system Node is required for the adapter; the later NetClaw runtime policy is still independently enforced.

Local evidence: `src/assistants/provider.ts` already does this for Copilot, but its terminal previews hardcode `node` and say Node >=22. `build.mjs` bundles the adapter with target `node22`. The [VS Code 1.102 API source](https://github.com/microsoft/vscode/blob/1.102.0/src/vscode-dts/vscode.d.ts) explicitly documents `process.execPath` for `McpStdioServerDefinition.command` and a child process of the extension host. [Electron's environment documentation](https://www.electronjs.org/docs/latest/api/environment-variables) describes `ELECTRON_RUN_AS_NODE` and notes that the runAsNode fuse can disable it. **Accessed 2026-10-17.**

Qualification must launch the actual bundled adapter with PATH containing no `node`, complete MCP initialize/list-tools, and verify the runtime major/capabilities on macOS and WSL. An editor/runtime path that disappeared after an update must fail with a re-register action, never fall back silently to a PATH binary. Capture and validate paths locally, shell-quote only in displayed terminal instructions, and execute argument arrays. No product secret appears in the registration command.

The reviewed previews have these shapes, with exact paths supplied by the extension:

```text
codex mcp add <unique-name> --env ELECTRON_RUN_AS_NODE=1 -- <editor-execPath> <adapter> --registration <private-file>
claude mcp add --env ELECTRON_RUN_AS_NODE=1 --transport stdio --scope local <unique-name> -- <editor-execPath> <adapter> --registration <private-file>
```

[Official Codex MCP documentation](https://learn.chatgpt.com/docs/extend/mcp?surface=cli) supports `--env`, stdio command/args and shared CLI/IDE configuration in `~/.codex/config.toml`, with trusted-project `.codex/config.toml` also supported. The CLI preview changes the user's Codex configuration and must say so. [Claude MCP documentation](https://code.claude.com/docs/en/mcp) supports this delimiter/env syntax and distinguishes local scope in `~/.claude.json`, project scope in `.mcp.json`, and user scope. Keep Claude local scope explicit; never promise that `--scope local` means a project-local file. Use unique setup-session names so registrations for different claws do not collide. **Accessed 2026-10-17.**

**Skill source decision.** Author the user-facing skill at `installer/assistant-skills/netclaw-install/SKILL.md` with relative supporting resources. Bundle a stamped copy under extension resources. Keep it out of the product-development `.agents/skills` and deployed network-operations `workspace/skills` inventories. Its first instruction distinguishes creating a deployment from developing NetClaw. Use one question sequence and plan contract across clients.

| Client | Supported target for deliberate installation | Notes |
| --- | --- | --- |
| Codex terminal | Deployment workspace `.agents/skills/netclaw-install/`; optional user `~/.agents/skills/netclaw-install/` | Do not default to deprecated `.codex/skills`. |
| Claude Code terminal | Deployment workspace `.claude/skills/netclaw-install/`; optional user `~/.claude/skills/netclaw-install/` | Do not overwrite an existing skill with another source hash. |
| Copilot | Bundled extension `chatSkills` contribution on VS Code >=1.109; optional workspace `.github/skills/netclaw-install/` | Avoid installing duplicate copies into all shared discovery roots. |

[Official OpenAI skills documentation](https://learn.chatgpt.com/docs/build-skills) documents `.agents/skills` discovery from current directory to repository root and the user's `~/.agents/skills`. [Claude skills documentation](https://code.claude.com/docs/en/skills) documents `.claude/skills` project/personal locations. [VS Code skills documentation](https://code.visualstudio.com/docs/agent-customization/agent-skills) documents `.github/skills`, `.claude/skills` and `.agents/skills` discovery. Scope selection, collision behavior, exact destinations and source hash must be shown before writing outside the extension bundle. Discovery alone does not prove the model invoked the skill; acceptance transcripts must prove it. **Accessed 2026-10-17.**

**Broker decision.** On macOS and WSL use a per-window Unix-domain socket in a short private directory, with an unpredictable identifier, owner-only directory/socket/registration permissions and a high-entropy token. Keep the token only in the owner-only registration file; do not print it in MCP definitions or return it from tools. Bound message sizes, validate schemas, reject unknown request types, bind requests to registration/session/host IDs, expire pending review requests and rotate on restart. Re-read enabled state on every adapter operation. Socket disconnection/heartbeat loss prevents advancing to another apply checkpoint; adapters cannot keep installation running after editor shutdown.

The stable [`node:net` IPC API](https://nodejs.org/api/net.html#ipc-support) supports filesystem Unix sockets on both target OSes and documents macOS/Linux path-length limits (typically 103/107 bytes) and stale socket cleanup after crashes. Avoid newer `BoundSocket` APIs unavailable at the chosen Node baseline. Short paths need explicit byte-length tests, not character counts. Stale cleanup requires ownership/session evidence; never unlink an arbitrary path. **Accessed 2026-10-17.**

**Authority decision.** Provisioning MCP methods can inspect catalog/prerequisites, draft/validate/explain plans, open native review/secret entry, and retrieve redacted progress. Opening a secret form returns only pending/completed state and a secret-reference ID. The adapter never receives the entered value, an approval token, or an apply operation. Requesting a form/review is not read-only: mark it truthfully. A headless or expired broker permits bounded inspection only. A spec or assistant can submit a plan; only the native UI or an operator's interactive terminal review may approve that exact revision/hash. Client approval settings, `allowed-tools` metadata, prompt wording and skill instructions are not the security boundary, because clients can auto-approve tools and same-user terminals remain outside the adapter sandbox.

**Rejected alternatives and limits.** No npm/npx bootstrap for the adapter; no copying editor runtime binaries; no shared network listener; no exposing the broker token as client environment variables; no generic shell tool; no secret-bearing MCP elicitation; no trust in a claimed “approved” plan field. Automatic skill pickup and client runtime behavior need real client tests with isolated configuration, recorded versions and redacted transcripts. No live client acceptance occurred during this research.

## R13 — Spec Kit 0.7 preset packaging

**Decision.** Pin development/fixture compatibility to Spec Kit **v0.7.1**, commit `c12293c3dac84bf20fccb7dfc455a76792d7a6d6`, verified through GitHub's tag tree API. The local `.specify/integration.json` and `init-options.json` actually say **0.7.1.dev0**, so the plan must retain that distinction rather than claiming the current workspace is a stable 0.7.1 installation. Do not update the product's development Spec Kit in place for this feature.

Package `installer/spec-kit/netclaw-claw/preset.yml` plus `templates/` and `commands/`. Use `schema_version: "1.0"`, preset identity/version/license, `requires.speckit_version`, and `provides.templates` entries of `type: template` or `type: command`, with `name`, `file`, and explicit `replaces`. The [v0.7.1 scaffold manifest](https://github.com/github/spec-kit/blob/v0.7.1/presets/scaffold/preset.yml) is the normative example, not newer main-branch documentation. **Accessed 2026-10-17.**

Install into a fresh deployment workspace outside the NetClaw checkout, using the pinned Specify CLI and `specify preset add --dev <verified-preset-directory>`. Verify `specify preset resolve` for each supplied artifact and inspect the resulting command/skill files before declaring the preset active. Project-local overrides precede presets; presets precede extensions and core templates. A higher-precedence user override can change behavior, so show effective resolution and refuse to imply NetClaw's safety workflow is active if its command content is displaced. The [v0.7.1 presets README](https://github.com/github/spec-kit/blob/v0.7.1/presets/README.md) documents the stack, local installation and command overrides. Local `common.sh:249` confirms the same template-resolution order. **Accessed 2026-10-17.**

Inspecting [v0.7.1 integrations](https://github.com/github/spec-kit/tree/v0.7.1/src/specify_cli/integrations) and [the command registrar](https://github.com/github/spec-kit/blob/v0.7.1/src/specify_cli/agents.py) establishes the actual layouts: Codex `.agents/skills/speckit-<name>/SKILL.md`, Claude `.claude/skills/speckit-<name>/SKILL.md`, Copilot `.github/agents/*.agent.md` with `.github/prompts/*.prompt.md` companions. The older preset README's `.claude/commands` example is not authoritative over this release's implementation. Test each integration separately in a clean deployment workspace; then test intentional multi-client installation and collisions. **Accessed 2026-10-17.**

The preset should replace the six requested workflow commands and relevant spec/plan/tasks/constitution templates. Deployment spec/clarification gather the canonical tree; planning produces the schema-valid `claw-plan.json` plus an explanation; tasks describe review, credential entry, apply and verification; analyze checks plan/spec/task agreement; implement submits the exact plan for native review and waits for report state. It never runs the installer itself. Report write-back is the default redacted Claw Report and preserves unknown/failed outcomes. Detailed private reports require the separate explicitly reviewed export.

**Critical integration finding.** The [v0.7.1 Copilot integration source](https://github.com/github/spec-kit/blob/v0.7.1/src/specify_cli/integrations/copilot/__init__.py) appends `--allow-all-tools` to automated CLI dispatch unless `SPECKIT_ALLOW_ALL_TOOLS=0`. This feature targets interactive Copilot/Claude/Codex conversations. Do not use Spec Kit's unattended workflow dispatch as an install executor. The fixed tool/broker review boundary must still reject apply even if a client is fully permissive. **Accessed 2026-10-17.**

**Rejected alternatives and limits.** No mutation of this repository's current development skills/presets to install a user's claw; no latest-main Specify dependency; no unverified new preset schema; no script-hook installation side effects; no treating generated prose as executable configuration. Fixture CLI installation should use an isolated environment and temporary HOME; this research did not install or execute Specify. A successful manifest parse is insufficient: render all three integrations, resolve templates, verify plan generation and review submission, and prove no autonomous apply path.

## R15 — VS Code minimum

**Decision recommendation.** Raise this feature's extension minimum to **VS Code 1.109.0**, and use `contributes.chatSkills` for the bundled Copilot skill. This makes native skills, slash invocation, extension contributions and `.agent.md`/prompt integrations part of the supported baseline, rather than depending on an experimental flag. Raise matching `@types/vscode` if code uses newer APIs. Existing users on 1.102–1.108 can retain the previous extension version and receive a clear upgrade requirement; do not change their existing installations or connections.

[MCP was GA in 1.102](https://code.visualstudio.com/updates/v1_102), and the pinned 1.102 API source includes the MCP provider already used locally. [1.107 introduced experimental Claude skills](https://code.visualstudio.com/updates/v1_107). [1.109 made Agent Skills GA/default and added `chatSkills`](https://code.visualstudio.com/updates/v1_109#_agent-skills-are-generally-available). Its [tagged discovery source](https://github.com/microsoft/vscode/blob/1.109.0/src/vs/workbench/contrib/chat/common/promptSyntax/config/promptFileLocations.ts) includes the standard project/personal discovery locations. **Accessed 2026-10-17.**

An alternative is retaining 1.102 for management and wizard functionality while gating native Copilot skills and Spec Kit custom-agent functionality to 1.109, with a tested prompt-file fallback. That preserves broader compatibility but adds a second assistant acceptance path. Do not claim automatic `SKILL.md` discovery on 1.102. Given all assistant stories are required, a single 1.109 installer baseline is the simpler qualified design.

## Corrections to carry into plan, contracts and tasks

1. Spell out exact Ubuntu allowlist/architecture qualification and distinguish a detected Windows distribution candidate from verified Linux OS identity. Existing Ubuntu 26.04 evidence does not qualify 24.04 or Spec 153.
2. Separate the unchanged/read-only Windows gate from the explicit reopen handoff, including its private resume-state write and possible VS Code Server installation. Do not promise a no-change snapshot across a deliberate reopen action.
3. Specify byte-aware WSL output decoding and distribution-name joins; never use English headers or machine-default WSL version as proof.
4. Replace terminal `node` previews with the editor runtime, explicit environment and unique registration names. Add no-PATH-Node MCP smoke tests on actual editor hosts.
5. Use the dedicated install-skill source location and supported per-client targets. Do not mix the skill into product-development or deployable network skill inventories.
6. Resolve minimum VS Code explicitly: recommendation is 1.109; the alternative requires feature gates and a fully tested older Copilot fallback.
7. Distinguish installed Spec Kit `0.7.1.dev0` from the pinned stable fixture release. Verify preset command rendering from source, not stale README examples.
8. Keep Spec Kit implement/assistant operations limited to plan submission; do not invoke automatic Copilot dispatch or let client auto-approval become installation approval.
9. Record all Windows/WSL, real client discovery, editor-runtime and cross-host resume cases as pending until live/disposable-host evidence exists. Unit fixtures are not host qualification.
