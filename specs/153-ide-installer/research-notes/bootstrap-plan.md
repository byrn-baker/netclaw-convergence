# Bootstrap and plan research — R4, R5, R6

Research date: 2026-10-17. Repository observations are from the Spec153 branch based on 1.11.0. No prerequisite remedy, source installer, runtime or provider was executed. The following decisions constrain implementation.

## R4 — Prerequisites and remedies

Use VS Code's bundled runtime for observation and source acquisition, then a selected Python 3.10+ interpreter for the standard-library engine. Read bundled copies of `config/installer-runtime.json` and `config/installer-preflight.json` before a checkout exists; verify copies against their source at build time. Probe executables by bounded argument-vector invocations. Never source a user's shell startup files to discover version managers or credentials.

Preserve the component-specific Node requirements: the repository's OpenClaw policy is >=24.16 <25 or >=26.1, while the HUD is >=24.19 <25 or >=26.1. Current [OpenClaw Node compatibility](https://docs.openclaw.ai/install/node-compatibility) confirms the former range and recommends Node 26. A satisfying arbitrary Node binary is not proof that its sqlite behavior or the selected HUD works; verify the actual executable and prerequisites per component. Do not silently replace the user's global Node or choose an unsupported current release.

Present fixed, platform-specific remedies in a visible terminal after native review: Xcode Command Line Tools on macOS when Git/build tooling needs them; Homebrew presence and supported-platform guidance; an isolated uv/Python environment; or Ubuntu apt prerequisites. Existing nvm/fnm/volta selections take precedence when compatible. Version-manager discovery is observational, not permission to edit profiles. [Homebrew installation](https://docs.brew.sh/Installation) currently prioritizes Apple silicon and macOS 15+, with Intel tier limitations; label those remedy limits separately from NetClaw's platform classification. [uv installation](https://docs.astral.sh/uv/getting-started/installation/) documents `brew install uv` and standalone installation. Downloading/executing an installer is a disclosed remedy, never a probe. [PEP 668](https://peps.python.org/pep-0668/) requires avoiding package writes to externally managed interpreters; use existing per-component venv/uv isolation. Never pass sudo to background extension jobs. OS password entry belongs to the visible terminal.

Docker executable presence, daemon readiness and selected image availability are separate facts. Checking readiness must not pull images or start the daemon. WSL systemd PID1 and a functioning user manager are explicit service prerequisites; missing controls retain production intent and stop apply. Opening setup and running the native Windows gate perform no remedies or downloads.

Rejected: one global Node requirement; automatic Homebrew installation; `pip --break-system-packages`; hidden elevation; calling installation commands to test availability; treating a remedy terminal's exit status as proof. Re-probe the required postcondition.

## R5 — Source acquisition and trust

Default to the [GitHub latest published release endpoint](https://docs.github.com/en/rest/releases/releases#get-the-latest-release) for `automateyournetwork/netclaw`; resolve its exact tag to a commit with [git ls-remote](https://git-scm.com/docs/git-ls-remote), including annotated-tag peeling. `main` is an explicit alternate with a stability warning. The latest tag is not necessarily a published release. If the release API is unavailable or rate limited, offer an explicitly labelled tag candidate selection, cached previously verified release or retry; never silently represent the highest tag as the latest release. No personal token is needed for public acquisition; never borrow existing claw credentials.

Use validated HTTPS origin, strict ref syntax, argument-vector Git commands, disabled prompts/hooks/submodules, a clean bounded Git configuration and no inherited credential helper. Preserve standard trusted TLS validation. Explain corporate CA/proxy failures; do not set `sslVerify=false`. User-supplied proxy URLs containing credentials are not stored in plans. [Git configuration](https://git-scm.com/docs/git-config) documents URL rewriting, hooks, credential helpers and protocol configuration; those can change the effect of an apparently fixed clone command and therefore must be controlled. Respect [GitHub rate limits](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api) and present bounded retry information rather than polling.

Acquire into a new destination, resolve real paths and refuse symlink aliases/occupied destinations. Record origin, requested channel/ref, resolved commit and a tree fingerprint. Read `config/setup-engine.json` as bounded JSON data before executing checkout code. It declares protocol major/minor, schema/catalog versions, entry point and supported interpreter. Unsupported/missing manifests stop setup with an explanation; a previous 1.11 release is not assumed to contain Spec153. Do not secretly fall back to main. Revalidate origin, tree, commit and manifest before review and apply.

Existing checkouts are inspected before choices. Dirty source may be reviewed and used as-is with an explicit tree fingerprint and changed-file disclosure; it cannot claim release provenance. Clean updates are offered only when source ownership evidence proves no existing installation depends on the checkout. Otherwise acquire a separate source. Mutable builds/MCP checkouts go into per-installation source work areas; a shared checkout is never a writable build cache for a second installation.

Rejected: running an unknown checkout to discover its protocol; silently fetching/pulling an existing installation's checkout; using a release tag as a signature/security guarantee; passing shell-expanded paths/refs; disabling TLS; turning fallback tags into release claims.

## R6 — Plan format, validation and hashing

Publish a closed JSON Schema 2020-12 document and implement the exact used validation subset in Python 3.10+ stdlib. The runtime must fail closed for unsupported schema keywords, unknown object fields, duplicate JSON keys, non-finite numbers, floats, oversized inputs, excessive nesting, lone surrogates and invalid references. Cross-field semantic validation covers unique installation IDs, canonical path collisions, provider/harness compatibility, component/skill/profile joins, secret scopes, endpoints and review policy. Do not claim to implement arbitrary JSON Schema; run development-only reference-validator conformance vectors for the published schema. See [JSON Schema 2020-12 core](https://json-schema.org/draft/2020-12/json-schema-core) and [Python JSON behavior](https://docs.python.org/3/library/json.html).

Canonical form is explicitly **NetClaw plan canonical JSON v1**, not a claim of RFC 8785 compliance: ASCII property names, bounded integers, Unicode scalar strings, arrays in declared order, UTF-8, lexicographically sorted object keys, no insignificant whitespace, no trailing newline, no floats. Hash with SHA-256. ASCII keys remove the UTF-16/property-sort ambiguity described by [RFC 8785](https://datatracker.ietf.org/doc/html/rfc8785). Human-facing saved files may use indentation; hash is independent of formatting. Version changes require an explicit reviewed migration; unknown major versions stop.

All settings use catalog IDs. Secret-classified fields contain only `{kind: "secret", key, owner, source}` references; non-secret fields use a typed `{kind: "value", value}` branch and catalog-specific validation. Unknown fields are confidential and rejected, not echoed in diagnostics. Known credential patterns are a secondary check, not proof that arbitrary secrets are detectable. Free-text identity content and inventory are external file references with content digests and a native private-content review; they must not be copied into assistant payloads. Diagnostics contain JSON pointers/reason codes and safe symbolic IDs, never rejected values.

The plan includes source identity, observed host binding, selected-home ownership, per-claw identity/harness/provider/model/channels/capabilities/settings/endpoints, Risk inheritance/mode, inventory/identity references, posture and selected verification tiers. Drafts can record unresolved decision IDs and assumptions; apply requires none. A native review capability is transient, one-use, bounded-lived and binds the canonical plan hash, target fingerprint, source fingerprint and reviewed effects. It is never embedded in the saved plan or returned by an assistant tool. A hash alone is not authority.

Rejected: permissive unknown keys; regex-only secret protection; env files or credentials on argv; floating-point cross-language hashes; executing schemas or remote `$ref`; persisted plaintext review tokens; a fixture mode accessible through production plan data; accepting a file written by an assistant as proof of human approval.
