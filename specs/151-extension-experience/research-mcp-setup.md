# Spec 151 research: per-MCP setup and execution

**Date:** 2026-10-11
**Scope:** Read-only source research for accepted clarification C. No installer, registration, service restart, live credential write, packaging, push or deployment was performed. This document recommends implementation boundaries; it does not claim the recommended actions are implemented or qualified.

## Decision

Use one explicit setup descriptor per integration card, joined to the existing environment map, installer component IDs and canonical MCP registrations. Keep configuration saves separate from installation, registration and lifecycle actions. Execute only named, implementation-owned operations after a review bound to the selected extension host and installation. Reuse existing writers, runtime staging helpers, registration mergers and lifecycle controllers through a small scoped operation coordinator.

The existing full installer is **not** a scoped per-MCP execution primitive. `scripts/install.sh --add "component"` preserves the component manifest, but still runs core prerequisites/runtime/onboarding, token installation, command linking, configuration and skills deployment, environment defaults and readiness. Do not wire a card's Execute button directly to that command while describing the effect as only installing that MCP. It remains useful as a reviewed, honestly described manual command where a bounded operation is unavailable.

### Metadata issues requiring resolution

1. Card IDs are not uniformly installer IDs: `rag` → `rag-mcp`, `catc` → `catalyst-center`, `arista` → `arista-cvp`, `paloalto` → `panorama`, `nvd` → `nvd-cve`, `clab` → `containerlab`, `drawio` → `drawio-rfc`, `azure-network` → `azure`. `thousandeyes` represents multiple alternatives and `wiki` combines several reference integrations. Some cards represent skills or services rather than installable MCPs. Use explicit joins and expose a component/variant choice when needed; do not derive shell arguments from display IDs.
2. `ENV_MAP` contains duplicate `catc` declarations at approximately `server.js:401` and `:436`; JavaScript silently uses the latter. Resolve the actual supported Catalyst Center fields using its canonical server and skill before moving metadata to a shared module. Do not retain both conflicting descriptions as if both were authoritative.
3. `GET /api/hud/configuration` is presence-only and is the safe baseline. `GET /api/env/:integrationId` exposes partial masked prefixes through `maskValue`; the extension should not switch to that route merely to get per-card metadata.
4. Shared keys belong to multiple cards (`NETCLAW_USERNAME`, `NETCLAW_LAB_MODE`, generic `READ_ONLY_MODE`, etc.). The review must disclose their shared use. Saving a controller endpoint or runtime security switch is a configuration change, not proof of endpoint connectivity or altered running policy.
5. A secret-name regex is insufficient: `CVPTOKEN`, `F5_AUTH_STRING`, `JENKINS_AUTH_BASE64`, `CCC_PWD` and certificate/private-key fields illustrate inconsistent naming. Unknown fields should remain confidential by default until explicit field metadata is present. Durations such as `GNS3_TOKEN_TTL` are not secrets merely because their name contains TOKEN.
6. Hermes conversion materializes some `.env` values into `config.yaml`. A successful `.env` save therefore does not imply existing Hermes server environment blocks were refreshed. Keep a distinct, explicitly reviewed registration/configuration refresh step and verify the effective registration privately.

## Recommended operation matrix

The following is a realistic initial implementation boundary, subject to isolated verification. Every unavailable action needs a visible explanation and applicable manual guidance; it must not appear as a working button.

| Operation | Proposed supported scope | Existing primitive and required adapter | Verification / honest result |
|---|---|---|---|
| Configure fields | Every integration in known field metadata, including known cards with no env fields | Existing environment writer with a scoped descriptor, explicit keep/replace/clear, identity check and a revision-aware adapter | Verify changed keys privately on server; return presence and saved revision. Report saved configuration only. Unknown fields are masked and have an explicit metadata limitation. |
| Prepare or stage command | Every known component with a documented applicable setup procedure | Existing command-document + `terminal.sendText(command, false)` pattern, explicit runtime/home environment | “Staged; not executed.” Full `install.sh --add` guidance describes its broader existing effects. No secret values in command text. |
| Install pyATS runtime | Mac or supported Linux/WSL/Remote Linux host, existing installation, prerequisites ready, explicit managed destination | `setup-pyats-runtime.py --target <selected-home>/pyats-venv`; optional separately enumerated pyATS launcher migration reused from current component installation | Verify the managed generation marker, pinned revision, interpreter imports and migration values. Preserve testbed/other `.env` keys. State installation/launcher ready independently of registration or device access. |
| Install GAIT runtime | Same host scope; required reviewed GAIT source already available in selected checkout | `setup-gait-runtime.py --target <selected-home>/gait-venv --python <approved-interpreter>` and selected-home launcher binding if needed | Existing staging helper verifies package versions and `gait_log` discovery before promotion. Verify binding separately. Retained `.previous` is recovery, not an invitation to erase an earlier backup. |
| Install other local components | Only add execution after auditing the individual existing installer function's writes and proving it can run without global core phases, sudo, interactive prompts or unrelated deployment | A bounded installer entry point may reuse `component_install_<id>`, component-specific runtime context and existing preflight/pip helper. Do not source-and-run an arbitrary function name from a webview | Default to guidance/staging when audit is incomplete. Remote HTTP or on-demand `npx`/`uvx` integrations may have no persistent installation step; label that truthfully. |
| Register canonical OpenClaw MCP | Explicit known component/variant with installed prerequisites; private bridge excluded; preserve custom entries | `install-mcp-config.py --repo … --runtime-root … --components <one-approved-component> --output <private-op-file> --config <selected-config>` wrapped with expected revisions, baseline and operation serialization | Read back selected names and normalized launch data; compare unchanged unrelated config. Exit zero alone is insufficient. A grouped component review must name every registration it changes. |
| Register Hermes MCP where no block exists | Selected canonical component, existing selected Hermes home | Generate selected JSON with `install-mcp-config.py`, then use existing converter | Inspect active `mcp_servers`, enabled state and values privately. Missing credentials = registration present but configuration required. |
| Register/update Hermes MCP with existing block | Requires a bounded addition to the existing converter before direct execution is advertised | Add selected-entry ownership tracking, custom-entry conflict refusal, expected-revision checks and preservation for unrelated YAML. Existing sidecar-only behavior remains an honest manual fallback if an advanced YAML structure cannot be preserved | Inspect actual config, not sidecar existence. Include preservation tests for existing enabled flags, timeouts, operator env, comments/anchors or a deliberate refusal for unsupported documents. Never claim the old converter's sidecar exit zero means registered. |
| Restart N2N/federation service | Only a dedicated N2N/federation service descriptor, existing owned installation/daemon and reviewed interruption scope | `federation-control.py restart` with selected-runtime environment and API/file identity checks | Same installation/runtime, new owned PID and defined ready state. Check/report active peer work before confirmation. This is “Restart federation service,” not “Restart any MCP.” |

Provide truthful native-runtime guidance only where documented | Do not substitute gateway restart, HUD restart, `pkill`, killing listeners or broad `openclaw mcp reload`. Saving settings must not perform any of these implicitly. |

`hermes-hud` is a protected control plane, not an ordinary registration target. Existing installer scripts exclude its MCP from agent-visible registration; retain that invariant. UI should explain its separate companion setup rather than adding it to normal MCP tool catalogs.

## Minimal coordinator design

1. **Descriptor and target binding.** Add a shared static descriptor source containing integration ID, component/variant IDs, field metadata, documentation and approved operation IDs. Keep command construction outside the webview. Obtain canonical checkout/runtime-home paths from an explicit reviewed binding or a trusted supporting endpoint; the current runtime API does not return them. Verify real paths and existing installation identity without creating a fresh identity. Do not infer runtime paths from the label or editor workspace.
2. **Prepare before confirmation.** Revalidate the trusted connection generation, host context, runtime kind, selected-home identity, executable/script existence, known operation, declared platform and prerequisites. Produce a concrete review with exact files/components/registrations affected, command without secrets, network downloads if any, interruption and recovery behavior. Record hashes of relevant config, manifest, managed-state and helper inputs, not their contents in visible output.
3. **Execute a fixed operation.** After an explicit action-specific confirmation, immediately recheck API identity, file identity and prepared hashes. Use `spawn`/`execFile` with fixed argv and `shell:false`; preserve the real OS HOME and set only selected-runtime variables. Clear inherited opposite-runtime and conflicting configuration overrides. Do not accept arbitrary command lines, target paths or environment maps from the webview. Persist an operation ID and state before launching.
4. **Serialize scoped writes.** One active setup operation per selected installation; reject a second operation until the first result is known. Add expected-revision checks to touched underlying config helpers so another writer cannot silently invalidate a reviewed plan. Merely doing a UI read-before-write is not an atomic precondition. Preserve private originals and helper-owned generation recovery.
5. **Display safe progress.** Expose phase/status messages from the coordinator (preflight, staging, registering, verifying). Arbitrary package-manager stdout, tracebacks and generated YAML can contain credentials; do not forward raw output into the webview, Output channel or audit. Keep only private bounded diagnostic output if necessary and publish controlled result codes, counts, timestamps and affected field names. Never include secret values in process argv.
6. **Verify the stated effect.** Reuse configuration-only readiness for artifact and registration checks. A separately described bounded discovery step can establish discovery but does not establish device/API operations, and Hermes direct discovery does not prove agent visibility. No tool invocation against devices is needed for setup acceptance.
7. **Cancellation and interruption.** Cancel before launch means no writes. After launch, signal only owned children if the helper supports cancellation and record that partial changes may remain. Closing a card is not cancellation. If the extension host stops or a result is lost, retain interrupted/unknown state; recover by inspecting the operation and underlying files, never by automatically replaying install/register/restart. For federation, an interrupted controller can leave an owned daemon running: inspect identity/status before determining outcome.

## Field schema and scoped save recommendation

Each field needs `key`, stable `label`, `description`, `kind` (`secret`, `text`, `url`, `path`, `boolean`, `number`, `enum`), requirement (`required`, `optional`, `conditional`, `unknown`), safe example, and shared-use information. Derive declared requirements from `config/installer-access.json` where applicable and reconcile with `.env.example`, canonical registrations and implementation readers; do not label every unlisted requirement optional. Authentication alternatives such as ServiceNow basic/OAuth/API-key are conditional (see `installer-readiness.py:85`). Unknown metadata is an explicit state.

For secrets, default to **Keep current value**, with separate Replace and Clear controls; a blank untouched input is never sent. Send changes only for the selected integration's allowlisted keys. Use persistent labels and semantic groups such as Connection, Authentication and Advanced. A presence-only API can still edit non-secret fields by showing set/unset and a blank replacement field; adding current non-secret values is optional and requires explicit safe classification. Never read full `.env` content into the webview.

For save verification, existing presence checks cannot distinguish “replaced with requested new secret” from “old secret still set.” Prefer the trusted configuration service comparing the submitted value internally and returning a sanitized field result plus revision. Retain original write authority and installation checks; add no automatic restart or endpoint probe on Save.

## Required verification

- Descriptor coverage: every known card receives its own matching fields or an honest no-fields/unknown descriptor; all ID aliases and grouped variants map to the canonical installer/registration source; duplicate metadata keys are caught.
- Field behavior: keep/replace/clear; conditional auth; shared fields; URL/number/boolean validation; unknown fields remain confidential; unrelated keys and dotenv quoting remain intact. Sentinel secrets never appear in webview payloads, command documents, process argv, logs, errors or audit artifacts.
- Target fences: Mac host, WSL and Remote context; wrong home; opposite runtime env inherited; changed API identity; copied/stale binding; missing/changed helper; trust revoked; selection switched during review and execution; invalid/unknown operation and component IDs.
- Installation: use temporary runtime homes and fixture repositories/dependency runners; exercise actual owned staging flow where feasible, no global runtime install. Verify promotion/retained recovery, no changes on preflight failure, partial download failure, stale previous backup, cancelled child and no automatic retry. Include at least one real isolated install/probe for each enabled action rather than treating mocked process exit zero as qualification.
- Registration: both OpenClaw config layouts, custom launch conflict, unrelated credentials/timeouts/approval fields preserved, grouped registrations explicit, repeat idempotence, stale revision, write failure, private bridge excluded. Hermes existing-block sidecar behavior must be a non-success until actual selected registration is implemented and verified.
- Restart: use an isolated owned service fixture; foreign PID, reused PID/start time, foreign installation listener, missing runtime, timeout and active-work interruption; verify service readiness and exact target after restart. Do not run owner federation restart during development acceptance.
- Outcome fidelity: nonzero exit, zero with unverified readiness, zero with Hermes sidecar only, failed postcondition, dropped result, extension-host interruption and cancellation after partial write must never appear as setup succeeded.
- Platform evidence: Mac tests are not WSL/Remote qualification. Reuse existing cross-platform tests where applicable, run new selected-host acceptance when available, and record unavailable host checks explicitly. Native Windows remains unsupported; no new host-support claim is inferred.

## Rejected shortcuts

- Running the complete installer for a one-MCP Execute action without its broad effects in the review.
- Running `setup.sh` from a card: it is an interactive multi-platform credential wizard, not a scoped configuration API.
- Treating `register-all-mcps.py` as OpenClaw/Hermes registration: that file discovers and registers servers with **DefenseClaw**, including broad discovery behavior outside the selected card.
- Treating a successful process exit, manifest entry, source directory, generated sidecar or saved secret presence as runtime/endpoint readiness.
- Replacing missing lifecycle capabilities with gateway restarts or process-name killing.
- Expanding native runtime help/speculation into supported actions without qualification of the exact selected runtime version.

## Implementation scope conclusion

The visual per-MCP editor is a modest extension of an existing API. Safe execution is a distinct bounded addition: descriptor, target binding, prepared operation/audit, fixed runner, verifier and a small set of qualified operations. Start with real scoped pyATS/GAIT installation, selected canonical registration and the existing explicitly named federation lifecycle; keep all other cards fully useful through scoped fields and truthful reviewed setup guidance until their individual execution effects are qualified. This fulfills direct execution for supported operations without presenting every catalog entry as uniformly installable or restartable.
